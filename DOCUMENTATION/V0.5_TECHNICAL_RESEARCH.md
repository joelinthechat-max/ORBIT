# ORBIT v0.5 Technical Research

## Browser automation and USB packaging

The ORBIT bundle now vendors the Playwright Python package and dependencies into platform-specific project folders for CPython 3.12: Linux x86_64 (`VENDOR/LINUX`) and Windows x86_64 (`VENDOR/WINDOWS`). Playwright Python is Apache-2.0 licensed and its wheel carries license/notice files, which are retained in the vendor directories. Playwright requires browser binaries separately; each Playwright release is tied to specific browser builds. Its documentation says Chromium/Firefox/WebKit binaries are managed in OS-specific user cache directories by default and take hundreds of megabytes. For ORBIT, browser cache/profile/download paths are redirected into `DATA/` where possible. We do not bundle a second Chromium build: browser binaries are large, have their own distribution notices and OS dependencies, and a Linux browser cannot be reused on Windows. The user may configure an already-present browser, or install a compatible Playwright browser into the USB-specific directory with the included opt-in setup script. The core application and workspace tasks remain usable when no browser is present. [1] [2]

Playwright's headed automation may depend on host display libraries and desktop policy. Its Python package is bundled without globally installing it, but the browser binary and OS-level libraries are not part of this release. Thus the adapter is packaged, while zero-install browser launch is conditional on a browser being supplied or available. This limitation is reported in the portability report.

## Desktop control platform limits

PyAutoGUI's official documentation lists mouse, keyboard and screenshot automation on Windows/Linux/macOS, and states that its window-management functions are currently Windows-only. It states that PyAutoGUI currently handles only the primary monitor. ORBIT's alternate Linux route uses Pillow capture and fixed-argument `xdotool` calls under an X11 display, when available; it does not execute model-supplied shell text. This fallback is not a Wayland integration, and no claim is made that X11 behavior generalizes to Windows or Wayland. [3]

## Local model backend

The replaceable ORBIT client uses an OpenAI-compatible loopback endpoint. llama.cpp's project is MIT licensed and documents a CPU/GPU C++ inference engine, quantized GGUF support, an OpenAI-compatible HTTP server and structured JSON output. Its current multimodal documentation supports image input via a supported text model plus its multimodal projector (`--mmproj`) or a supported Hugging Face model identity. A generic `.gguf` file alone does not prove vision compatibility. An exact model architecture, chat template, quantization and projector must be checked. [4] [5]

ORBIT includes a user-controlled llama.cpp server launcher that expects the user to provide the platform-matched binary and model file under the USB folder. It uses loopback binding, CPU-only settings, bounded context/thread values, process timeouts and status reporting; it does not forecast model RAM or download weights/binaries. No real model server or weights were present in the execution environment, so this release's model-process tests are wrapper/fake-process tests only, not real inference. The 4 GB resource target is unverified.

## Environment observations

The available development session had an X11 display, `/usr/bin/chromium`, `xdotool`, Pillow screen capture, and Playwright 1.64.1. It had no PyAutoGUI module, no `llama-server` process or executable on the tested paths, and no vision/language service listening on the default ORBIT model ports. Tests use a new disposable browser profile and localhost fixtures, not the existing browser's user profile/debugging endpoint. The integration test is a real browser-session test where noted; it is not a clean Windows or 4 GB hardware test.
